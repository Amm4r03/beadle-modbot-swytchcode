Beadle

The moderation and community growth agent · Track 3 · Swytchcode buildathon

One shared agent state machine watches a community, judges every message with calibrated probabilities, acts inside policy, asks a human when unsure, and learns from every admin decision.

Demo moment: a genuine question gets answered while a polished scam is quarantined — same second, opposite outcomes, with the reason and the gate score on screen.

1 · The state machine — what happens at each stage

OBSERVE

Normalize + dedupe

No model call. Stable event ID, platform mapping, duplicate protection. Every event is written to the ledger before anything else.
CLASSIFY

Signals + one Jev call

8 deterministic signals (member_new, first_link, rate_burst, duplicate_payload, domain_allow_or_block, known_trust_or_override, solicitation, question_shape) + one batched Jev call with three typed questions: solicitation, question_shape, needs_human_review. Each answer is stored with its prompt hash and model.
GATE

Pure reducer — no model

solicitation ≥ 0.70 → quarantine · question_shape ≥ 0.85 + solicitation ≤ 0.10 + review < 0.50 → answer · otherwise review/deny. A fixed reason template names the decisive signals. Fail-closed: no Jev → human review.
ESCALATE

Quarantine card

No model call. The held case carries: event excerpt, gate score vs threshold, reason, model + prompt version, evidence IDs. A card is evidence for a human, not a verdict.
RESOLVE

Answer + execution

Answer drafting runs on the generation chain (Groq) only after the gate allows it — strict JSON, citations only from retrieved sources. Actions leave through the outbox into Swytchcode.
LEARN

Every decision is a label

No model call to store. An admin resolution becomes a labeled example; later, similar cases retrieve it and cite it — "because you taught me". No auto-promotion of examples into rules.

2 · How an event moves through the machine

observe→ classify→ gate→ escalate→ resolve→ learn

staged input · scores are from real recorded runs

Press simulate: a scam message walks the machine with its real recorded numbers (solicitation 0.98 → quarantine), then a genuine question (question_shape 0.94 → answer).

3 · The learning loop

1 · The gate quarantines an uncertain case → 2 · the admin resolves it with a label and a reason → 3 · the resolution is written back as a labeled example (event id, gate score, decision, timestamp) → 4 · a later, distinct case retrieves that example and the case card shows both IDs and what was carried over.

The card is the proof: two real records, zero fabricated IDs. Nothing is auto-promoted into a rule; a learned exception can never defeat an explicit block.
